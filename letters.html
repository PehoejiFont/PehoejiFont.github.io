Unicode & Encoding for POJ

An English font maps one key to one glyph. Taigi Pe̍h-ōe-jī (POJ) text is mostly base letter + one or two combining marks, and Unicode has no single precomposed codepoint for most of the results.

How POJ differs from an English font

Every character on a computer has a Unicode number: plain o is U+006F, and ready-made ó is U+00F3. For characters without a single number, Unicode attaches non-spacing combining marks (“stickers”) after the base letter:

oU+006F +  ͘U+0358 = o͘
aU+0061 +  ̍U+030D = a̍
oU+006F +  ́U+0301 +  ͘U+0358 = ó͘

Supporting Taigi Pe̍h-ōe-jī cleanly requires handling eight distinct typographic requirements:

RequirementWhy it is difficult for fonts
o͘ = o + U+0358
COMBINING DOT ABOVE RIGHT		 No precomposed o͘ exists. The dot sits at the top right, not centred above the letter like standard European diacritics.
o͘ + tone
ó͘ ò͘ ô͘ ō͘ ŏ͘ o̍͘ & capitals		 Two combining marks at once: tone centred above, dot at top right. They must not collide with each other, and the dot must not collide with the following letter (o͘h, o͘ⁿ, o͘").
8th tone U+030D
COMBINING VERTICAL LINE ABOVE		 No precomposed letter has it (a̍ e̍ i̍ o̍ u̍ m̍ n̍ are always multi-codepoint sequences). Most Latin fonts lack this glyph.
Syllabic m & n tones
ḿ m̀ m̂ m̄ m̍, ń ǹ n̂ n̄ n̍g		 Only ḿ ń ǹ (and capitals) are precomposed, and ḿ/U+1E3F and ǹ/U+01F9 live in blocks many Latin fonts skip. The rest are built from combining marks.
i + tone
í ì î ī ĭ i̍		 i has the Unicode Soft_Dotted property: its dot must disappear whenever an above mark sits on it. Precomposed í already does this; the sequence i + U+030D requires the font to swap in dotless ı.
Nasal ⁿ U+207F
SUPERSCRIPT LATIN SMALL LETTER N		 A modifier letter (Lm), not a combining mark. Many fonts omit it. Compatibility normalisation (NFKC) destroys it into plain n (see below).
Hyphens - and -- - joins syllables; -- marks the neutral tone (tńg--khì). Fonts and editors must keep -- as two distinct hyphens (see below).
Han-Lo (漢羅) & Ruby The Latin portion of a CJK font must support all of the above. Ruby (POJ over Han characters) uses either IVS (cmap format 14) or HTML <ruby> (see below).
Tone placement rule to remember when testing

In syllabic ng, the tone mark goes on the n: n̍g, n̂g — never ng̍.

Will Unicode ever encode a precomposed o͘ or a̍?

No. Nothing with U+0358 or U+030D is precomposed, and none will be added. UTC/WG2 policy forbids encoding new precomposed letters that can already be represented as base + combining mark. When POJ was proposed, Unicode encoded U+0358 (Unicode 4.1, 2005) rather than precomposed o͘. Furthermore, the Normalization Stability Policy (2001) guarantees that NFC of an existing sequence never changes, so no newly assigned codepoint could ever become the NFC form of o + U+0358.

Input forms & Canonical Combining Classes

The same visible syllable ó͘ can reach a font as at least three distinct Unicode sequences. Every POJ font must render all of them identically:

Three encodings of ó͘

FormCodepoint sequenceWhere it comes from
1. NFC (canonical precomposed)U+00F3 ó + U+0358Most web text, standard IMEs, NFC-normalising databases
2. NFD (canonical decomposed)U+006F o + U+0301 + U+0358macOS file names, some IMEs, PDF copy-out
3. Non-canonical mark orderU+006F o + U+0358 + U+0301Sequential / dead-key IMEs where the user types o͘ as a unit, then adds the tone
4. MixedAny mix of 1–3 in one fileDocuments edited across multiple apps or platforms
óU+00F3+  ͘U+0358 ≡ oU+006F+  ́U+0301+  ͘U+0358 ≡ oU+006F+  ͘U+0358+  ́U+0301

Canonical Combining Class (ccc)

MarksCanonical Combining Class (ccc)

Unicode normalisation sorts adjacent combining marks in ascending order of ccc. Therefore o + U+0358 + U+0301 becomes o + U+0301 + U+0358, and NFC composes that into ó + U+0358. Key consequences:

  • After normalisation, the tone mark always precedes the dot.
  • For tones 2, 3, 5, 7, and 9, NFC is precomposed toned vowel + U+0358. Fonts must attach U+0358 to ó ò ô ō ŏ Ó Ò Ô Ō Ŏ, not only to plain o O.
  • For the 8th tone, there is no precomposed vowel, so NFC of o̍͘ remains o + U+030D + U+0358.
  • HarfBuzz reorders marks by ccc and recomposes through the font’s cmap before running GSUB. Verified across all 24 audited fonts: o 0358 0301, o 0301 0358, and ó 0358 shaped identically. Thus in HarfBuzz, a ligature written only for o 0358 0301 never fires, and o acutecomb uni0358 never fires when the font maps ó — yet both rules remain essential for shapers that do not pre-normalise.
  • If a document mixes forms, text search for hō͘ can miss occurrences. Normalising documents to NFC resolves this.

How shaping engines join it up

HarfBuzz (Chrome, Firefox, Android, LibreOffice, Linux)

Verified experimentally in this study and against hb-ot-shape-normalize.cc / hb-ot-shape-fallback.cc:

  1. Normalise: decomposes, sorts marks by ccc, then recomposes wherever the font’s cmap maps the composite (Latin uses COMPOSED_DIACRITICS). If a precomposed letter is absent from cmap, HarfBuzz decomposes it into base + mark.
  2. GSUB ccmp: always enabled; cannot be disabled by users or CSS. Used for dotless-i, capital-form marks, and precomposed POJ ligatures.
  3. Other GSUB features: locl, liga, case, etc.
  4. GPOS mark / mkmk: anchor-based positioning.
  5. Fallback positioning — all or nothing: HarfBuzz computes geometric fallback positions from ccc and bounding boxes only if the font has no GPOS mark feature at all. If a font has mark but lacks an anchor for a specific base–mark pair, the mark stays at raw offset (0, 0).
    • Verified — Arial: has mark, no U+0358 anchors → dot stays at (0, 0), landing outside the advance box.
    • Verified — Source Sans 3: ŏ + U+0358 and Ŏ + U+0358 lack anchors → (0, 0).
    • Verified — Geneva, Helvetica, Menlo, and taigivs Latin: no mark table → fallback runs and lifts U+0358 above the entire ink box of Ó/Ō (accent included), causing the dot to float high above capitals.

CoreText (macOS / iOS / Safari) & DirectWrite (Windows / Word)

Verification status

Preliminary macOS CoreText tests have been run (see Platform Differences). Windows DirectWrite has not been tested directly; statements marked (not yet verified) are based on platform documentation.

  • Neither engine runs HarfBuzz-style ccc/bounding-box fallback positioning; unanchored marks draw at their outline coordinates (reviewer claim, not verified on DirectWrite; observed on CoreText).
  • DirectWrite is reported not to reorder marks or recompose NFD through cmap the way HarfBuzz does, so o + U+0301 may remain two glyphs and non-canonical orders may reach GSUB (reviewer claim, not verified).
  • When a precomposed letter (e.g. ḿ, ǹ, ŏ) is missing from cmap, both engines tend to trigger system font fallback rather than decompose it, causing a single mismatched letter (reviewer claim, not verified).
  • Apple system fonts (Geneva, Helvetica, Menlo) may rely on AAT tables (morx/kerx) under CoreText, so HarfBuzz results do not predict Pages or Safari rendering.

This is why a production POJ font must map every precomposed letter in the Unicode 17.0 matrix and cover both mark orders and both NFC and NFD inputs in GSUB ccmp.

Soft_Dotted i and j (dotless ı)

When an above-mark sits on i, the tittle (dot) must disappear, just as in í. Ready-made letters like í ì î ī ĭ already omit it, whereas i + U+030D (i̍) is always a sequence. The font must substitute i → dotlessi (U+0131) and j → uni0237 (U+0237) in ccmp.

Correctchi̍t (一) in Lesson One: dotless ı swapped in before U+030D
Wrongchi̍t in Taigi Huninn POJ (字咍): the dot stays under the 8th-tone line

Superscript ⁿ (U+207F) & Capital ᴺ (U+1D3A)

  • U+207F is a modifier letter (General Category Lm), not a combining mark. It carries its own advance width and needs no anchors.
  • NFKC/NFKD corruption: Its compatibility decomposition is <super> n, so NFKC/NFKD silently turns hiⁿ into hin (and thiⁿ into thin). Search indices, databases, and “normalise width” pipelines frequently apply NFKC and destroy nasalisation. Always use NFC, never NFKC, for Taigi text.
  • No case mapping: Unicode defines no uppercase mapping for U+207F, so "sⁿ".upper() yields Sⁿ. All-caps text sometimes uses U+1D3A ᴺ MODIFIER LETTER CAPITAL N (SIᴺ) or NN. POJ fonts should include U+1D3A.
  • .case form rule: A .case glyph for ⁿ may raise it to cap-height alignment, but must not swap ⁿ into ᴺ, because case should not alter semantic character identity.
  • Non-font errors: HTML <sup>n</sup>, subscript ₙ (U+2099), and feminine ordinal ª are incorrect character encodings, not font issues.

Ideographic Variation Sequences (Han-Lo ruby)

ButTaiwan’s 字咍 taigivs fonts (TaigiHuninn, TaigiIansui, TaigiKaiStd, TaigiGenRyuMin, etc.; fonts OFL 1.1) embed Taigi ruby directly into glyphs via an OpenType cmap format 14 table:

  • Each Han character followed by an Ideographic Variation Selector (U+E0100…) selects a glyph containing the reading drawn above it — 8,021 IVS mappings per font.
  • Includes POJ (白話字), HI (方音, Taigi Phonetic Symbols), KN (假名, Taigi kana), and dual-reading sets POJHI and POJKN.
  • Uses IVS only, no GSUB: switching the font file switches which annotation appears.
  • This is the only plain-text way to put POJ above Han characters without HTML <ruby>, and it is a separate track from Latin POJ support.
  • Caveats: The Latin portion of taigivs fonts has no GPOS mark table and no dotless-i swap (i̍ keeps its dot), so running POJ relies on HarfBuzz fallback. Web subsetters and PDF generators frequently strip cmap format 14 tables or drop variation selectors.

Hyphens & neutral-tone double hyphen (--)

  • Single hyphen - (U+002D) joins syllables; double hyphen -- marks the neutral tone: chhù--nih, khòaⁿ--tio̍h, tńg--khì (轉去).
  • Font rule: Never ligature -- into an en-dash via liga or calt, and keep enough sidebearing so the two hyphens do not touch.
  • Editor rule: Auto-correct features that turn -- into – corrupt POJ text and should be disabled.
  • Line breaking: Preventing a break between the two hyphens (chhù- / -nih) is a layout-engine concern. U+2011 NON-BREAKING HYPHEN is sometimes used, though many fonts omit it.
