檢測工具、研究方法與審查紀錄

完整彙整 PehoejiFont 專案背後的 11 支檢測與建置腳本、資料檔目錄、尚未驗證的研究問題，以及兩份 Gemini 4 同儕審查的查證紀錄。

tools/ 目錄下的 CLI 工具腳本

各腳本以儲存庫根目錄為執行工作路徑設計，供重現所有普查與實測數據：

腳本路徑用途說明相依套件
tools/build_catalog.py從 google/fonts 稀疏檢出建立 data/google-fonts.json（2,067 款家族的授權、RFN、設計師與上游網址）。Python 3 標準函式庫
tools/download_fonts.py為每款候選字型家族下載一支主要字型檔供覆蓋率檢測。Python 3
tools/check_coverage.py掃描下載字型的 POJ 字碼、組合聲調與 GPOS mark 功能，產出 data/shortlist.json。fonttools
tools/fork_repos.sh將 data/fork-list.tsv 中的 989 個獨立上游儲存庫（僅預設分支）批次 Fork 至 PehoejiFont 組織。gh CLI
tools/poj_font_audit.py單一字型完整 POJ 稽核：cmap 覆蓋、GSUB/GPOS 功能、U+0358／U+030D 錨點基礎字數、IVS 與 PUA 統計。fonttools、uharfbuzz
tools/poj_shape_test.pyHarfBuzz 整形探針，將每個 POJ 音節分類（ligature／gpos-anchor／zero-width-overstrike／FLOATING／NOTDEF）並比對 NFC 與 NFD。uharfbuzz
tools/poj_specimen.py輸出高解析度 PNG 樣張（每款字型並列 NFC 與 NFD 兩行）至 docs/img/specimen-*.png。fonttools、uharfbuzz、pillow
tools/poj_coretext.swiftmacOS CoreText 整形與 PNG 繪製探針；記錄 glyph ID、座標、名義進位寬度、外框盒與系統補字情形。macOS Swift / CoreText
tools/poj_coretext_compare.py將編譯後的 poj_coretext.swift 與 HarfBuzz 交叉比對（涵蓋 NFC、NFD 與反向順序）。uharfbuzz、Swift 探針
tools/poj_guide_svg.py以 HarfBuzz 實際座標與 fontTools 輪廓輸出本網站範例 SVG（支援 --boxes 與 --mark-color）。fonttools、uharfbuzz
tools/build_site_fonts.sh重建本網站自託管的源樣明體 Regular 與 Bold WOFF2 子集（英文輕量主檔＋繁體中文增量 CJK 檔），並保留 GSUB 閉包。fonttools、brotli（pyftsubset）

重建本網站的源樣明體字型子集

本站自託管精簡版的 源樣明體（GenYo Min） Regular 與 Bold：英文頁面僅下載約 85 KB 的基礎拉丁＋POJ＋英文頁漢字子集（GenYoMin2TW-{R,B}-site.woff2）；繁體中文頁面則額外按需載入 GenYoMin2TW-{R,B}-zhtw.woff2 補齊所有繁體中文漢字。日後新增頁面文字時，請於儲存庫根目錄執行：

shell — 重建網站源樣明體子集
tools/build_site_fonts.sh <含 GenYoMin2TW-R.otf 與 B.otf 的資料夾>

註：源樣明體並未在 cmap 單獨收錄無點 ı（U+0131）與 ȷ（U+0237），因此字型開發者指南中那兩個單獨符號會退回系統字型；一般白話字內文如 i̍ 則完全不受影響，因源樣明體的 ccmp 預繪字形本身已去點。

待進一步驗證的研究問題

  1. 完整 CoreText 與 DirectWrite 跨引擎矩陣：於 macOS（CoreText）與 Windows（DirectWrite）補完調號重排、NFD 重組、缺字補字與無錨點 U+0358 的完整實測。
  2. Google Fonts 跨切塊拆散測試：於 Chrome、Safari、Firefox 實測芫荽與粉圓的 o + U+0358 是否可能在 latin 與台語 unicode-range 切塊間被拆散。
  3. 尚未測試的社群字型：下載並對 Caivun、Kaukhia 與 Indeciso 執行完整檢測管線。
  4. 舊式替代編碼的真實分布：掃描 ChhoeTaigi 語料庫與早期台語網頁，量化中圓點、越南語帶角 o、PUA 與 8-bit 編碼在現存文本中的比例。

模型同儕審查與查證紀錄（Gemini 4）

docs/poj-font-implementation.md 初稿曾以無工具的純文字模式交由兩套 Gemini 4 XHigh 模型（gemini-4-neon-xhigh 與 gemini-4-hydrogen-xhigh）經由 agy 獨立審查，完整紀錄保存於 docs/reviews/。

兩份審查一致確認的核心論點

  • 標準組合類別（ccc=230 與 ccc=232）數值與正規化重排機制；
  • Unicode 17.0 預組 POJ／KPL 字表；
  • NFKC 會將 U+207F（ⁿ）破壞成普通 n；
  • i̍ 等組合序列的 Soft_Dotted 無點 i 需求；
  • HarfBuzz 在 GSUB 前執行正規化重排；
  • CSS 在非零 letter-spacing 下停用選用 liga。

已實測查證並採納的修正項目

審查提出的修正點本站查證方式與結果
HarfBuzz 備援定位為全有或全無（只要有任何 mark 功能便停用），解釋 Arial 的 U+0358 與 Source Sans 3 的 ŏ͘ 錯位。實測驗證：兩者在該處偏移量確實為 (0, 0)。
Lesson One、粉圓、芫荽與 WD-XL 皆含 mark／mkmk（屬 B + A，非僅 B）；僅源樣、豆腐烏與 taigivs 缺乏 mark。核對 data/poj-font-audit.json 中 GPOS 功能清單確認。
SIL 的佔位 U+0358 是 GDEF 類別 1 基礎字形，非附加符號。檢查 Charis、Doulos、Gentium 之 GDEF 表確認為類別 1。
U+1D3A 是大寫修飾字母 ᴺ，並非 ⁿ 的舊式寫法。核對 UnicodeData.txt 確認。
o̍͘ 的 NFC 形式仍維持 o + 030D + 0358。以 Python unicodedata 驗證確認。
HarfBuzz 在 GSUB 前亦會將 o + 0301 重組為 ó。比對 NFC 與 NFD 輸出字形串確認完全一致。
KPL 保留第六調腔調使用的抑揚符 U+030C。核對 Unicode 預組字元集確認。
網頁字型子集化可能拆散或遺漏 POJ 調號。實測確認且比預期更嚴重：Google Fonts 上的 TASA Explorer 與 Source Sans 3 完全刪除了 POJ 調號。
AFDKO 功能範本修正：最長優先連字、拆分 mark lookup、languagesystem、GDEF、mark filtering set、uni0237、o_uni0358 與 ő ǒ 基礎字、頂層 markClass、mkmk。已全數套用於字型開發者實作指南。
補充進階工程主題：雙連字號 --、垂直度量、case 預設關閉、o͘ 後方碰撞、小型大寫、CFF 與 TrueType、可變字型、PDF 字形命名、locl 互動與額外舊式編碼。已納入文件（部分項目尚未逐一跑實驗）。

保留標註「待實測」與未採納的項目

  • 標註為尚未獨立實測之審查意見：DirectWrite 重排／重組／補字細節；Microsoft Word 的連字預設狀態；額外舊式 PUA／8-bit／形似字在真實語料中的出現頻率。
  • 未採納或調整措辭：（1）「寫在前面的 2 字形連字會永久遮蔽 3 字形連字」——feaLib 與 makeotf 會在同一 lookup 內自動依長度降冪排序（規則 2 仍建議手動最長優先以確保跨工具相容）。（2）NunitoPOJ 無點 i 疑慮——已實測確認即使關閉 liga，NunitoPOJ 仍透過 ccmp 正確輸出 dotlessi + uni030D。
