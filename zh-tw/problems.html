疑難排解與跨平台差異

針對台語白話字（POJ）在畫面渲染、全文搜尋、網頁載入與 PDF 複製上最常見的 11 種異常症狀逐一排查，並比較 HarfBuzz、macOS CoreText 與 Windows DirectWrite 的行為差異。

依症狀快速診斷

1. 畫面上出現空白方框（□／豆腐字）

原因：該字型的 cmap 完全沒有收錄此字碼。例如 EB Garamond 沒有 U+0358；在 1,393 款待補字的 Google Fonts 候選家族中，也有 1,242 款同時缺少三個 POJ 字元（U+0358、U+030D、U+207F）。

解法：改用推薦清單中已驗證的字型。

2. o͘ 的圓點掉到字母右邊很遠，或高高飄在大寫上方

原因：字型雖收錄 U+0358 但未建立 topright 錨點（方式 D）。若字型為其他符號設了 mark 表（如 Arial，或 Source Sans 3 的 ŏ͘），HarfBuzz 會關閉備援並把圓點留在 (0, 0)；若全無 mark 表（如 Helvetica、Geneva、Menlo），HarfBuzz 備援會將圓點抬高至 Ó͘ Ō͘ 整個筆畫之上。

解法：改用方式 A+B 或方式 A 字型。切勿以手動空白或微調硬喬位置，換一台電腦就會破版。

3. 一個字詞裡有個別字母長得像別款字型

原因：字型缺少該預組字碼（最常缺 ḿ U+1E3F、ǹ U+01F9、ŏ、U+0358 或 U+030D），系統於是悄悄借用其他字型補字（例如 macOS 上 EB Garamond 會借用 Helvetica 的 U+0358）。

解法：選擇完整涵蓋 POJ 預組字集的字型（可至測試台驗證）。

4. i̍ 的聲調下方還留著 i 本身的圓點

原因：字型未在 ccmp 實作 Soft_Dotted 規則（上方附加符號前將 i → dotlessi；見說明）。字咍 Taigi IVS 字型、EB Garamond、Helvetica、Geneva 與 Menlo 皆有此現象。

解法：更換字型。切勿手動輸入無點 ı（U+0131），否則將破壞拼寫正確性與搜尋比對。

5. 加上 CSS letter-spacing 或在 Microsoft Word 開啟後突然破版

原因：該字型把 POJ 組字放在選用的 liga 或 clig，而非必定執行的 ccmp。依 CSS Text 3，設定非零 letter-spacing 時瀏覽器會停用選用連字；Word 預設也關閉連字功能。

解法：改用以 ccmp 實作的字型（本站推薦清單皆符合）。在 Word 內臨時應急可至「字型 → 進階」手動啟用連字。

6. thiⁿ 莫名其妙變成 thin（或 hiⁿ 變成 hin）

原因：資料庫、搜尋索引或全半形整理程式套用了 NFKC/NFKD 正規化，將 U+207F 透過 <super> n 分解成普通 n（見說明）。

解法：所有處理台語文字的系統務必設定為 NFC，嚴禁使用 NFKC 或 NFKD。

7. 畫面明明看得到某個詞，Ctrl+F 或資料庫卻搜尋不到

原因：文件中混雜了 NFC（ó + 0358）、NFD（o + 0301 + 0358）與反向順序（o + 0358 + 0301），或者使用了中圓點 o·（U+00B7）、越南語帶角 ơ（U+01A1）等形似字。

解法：將所有形似字替換為標準 U+0358／U+030D／U+207F，再整份正規化為 NFC。

8. 輕聲 tńg--khì 被變成 tńg–khì

原因：文書軟體的「自動將連字號取代為破折號」功能誤改，或字型在 liga／calt 內將 -- 連字成破折號。

解法：關閉編輯器的自動破折號取代設定，並確認所選字型保留兩條獨立連字號。

9. 本機電腦顯示正常，放到網站上圓點就壞掉

原因：網站可能從 Google Fonts CSS API 載入字型，而 Google Fonts 的 unicode-range 切塊會將 TASA Explorer 與 Source Sans 3 的 POJ 調號完全刪除（詳見實測）；過度精簡的本機子集化工具也可能誤刪 ccmp／mark 或 cmap format 14。

解法：將完整字型檔自行託管在網站上，或使用子集工具時明確保留所有 POJ 字碼與 --layout-features='*'。

10. 舊文件一換字型就變成怪符號或方框

原因：舊文件是以私用區（PUA，如早期 aiongg 字型的 U+E400–E435）或前 Unicode 時代的 8-bit 編碼（Windows-1252／MacRoman）繕打，離開原字型就失去意義。

解法：將舊文件一次性轉碼為標準 Unicode NFC 白話字，之後即可通行所有現代字型。

11. 從 PDF 複製出來的 POJ 文字變亂碼、多出空白或出現無點 ı

原因：常見三種 PDF 機制問題：（a）字型使用非 AGL 標準字形名稱（如 oopoj_acutecomb 而非 o_uni0301_uni0358）導致自動 ToUnicode 對應失敗；（b）SIL 佔位圓點（方式 C）可能讓 PDF 閱讀器誤判為詞間空白；（c）dotlessi + uni030D 若 PDF 輸出端未寫入 /ActualText，複製時可能還原成 ı̍。

解法：選用符合 AGL 命名規範的字型，並在支援的 PDF 排版軟體中啟用 /ActualText 標記。

跨平台與整形引擎差異

Chrome、Firefox、Android、LibreOffice 與 Linux 皆使用 HarfBuzz；Apple 原生程式（Safari、Pages、Keynote）使用 CoreText；Windows 原生程式（Microsoft Word、系統介面）使用 DirectWrite。

整形引擎使用環境本研究實測進度處理 POJ 的關鍵行為
HarfBuzz Chrome、Firefox、Android、LibreOffice、Linux 完整實測（24 款） 在 GSUB 前先正規化（ccc 重排＋cmap 重組）；缺少預組字母會自動分解；幾何備援定位為全有或全無（只要存在任何 mark 功能即全面停用）。
CoreText macOS / iOS 原生軟體、Safari、Pages 初步實測完成 Lesson One、jf open 粉圓、芫荽 Iansui、一點明體、源樣明體與 WD-XL 滑油字在所有測試音節的輸出皆與 HarfBuzz 完全一致。無 mark 表的字型（Helvetica、Menlo、字咍 Taigi 字型）與 HarfBuzz 差異顯著，因 CoreText 不做 HarfBuzz 式備援，且 Apple 系統字型可能使用 AAT（morx/kerx）。
DirectWrite Windows 原生軟體、Microsoft Word 尚未直接實測 （模型審查意見，待實測）：不會像 HarfBuzz 預先重排或重組 NFD，非正規順序會直接進入 GSUB；缺少預組字母時偏好觸發系統補字而非分解；Word 預設關閉 liga。
如何做到跨平台一致顯示？

優先採用以方式 A ＋ B 打造的字型（ccmp 預繪字形涵蓋 NFC／NFD／反向順序，加上完整的 GPOS mark／mkmk 錨點與全套預組字元 cmap），即可在 HarfBuzz、CoreText 與 DirectWrite 獲得最一致的結果。
