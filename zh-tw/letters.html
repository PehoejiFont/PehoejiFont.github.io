POJ 的 Unicode 編碼結構

英文字型基本上是一個按鍵對應一個字形；但台語白話字（POJ）大量由基礎字母＋一至兩個組合附加符號構成，而且大多數組合在 Unicode 中並沒有單一預組字碼。

POJ 與一般英文字型的八大差異

電腦中的每個字元都有專屬的 Unicode 編號：例如 o 是 U+006F，現成的預組字母 ó 是 U+00F3。對於沒有單一預組編號的字母，Unicode 會在基礎字母後面貼上不佔寬度的組合附加符號（combining marks）：

oU+006F +  ͘U+0358 = o͘
aU+0061 +  ̍U+030D = a̍
oU+006F +  ́U+0301 +  ͘U+0358 = ó͘

要完整支援台語白話字（POJ），字型必須同時處理以下八項排版需求：

需求項目對字型的技術挑戰
o͘ = o + U+0358
COMBINING DOT ABOVE RIGHT		 沒有預組字元。圓點必須位於右上方，而非一般歐洲語系重音符號的正上方。
帶調 o͘
ó͘ ò͘ ô͘ ō͘ ŏ͘ o̍͘ 與大寫		 同時疊加兩個附加符號：聲調居中於上方，圓點位於右上方。兩者不可互撞，圓點也不可撞到後方字母（如 o͘h、o͘ⁿ、o͘"）。
第八調 U+030D
COMBINING VERTICAL LINE ABOVE		 完全沒有預組字母（a̍ e̍ i̍ o̍ u̍ m̍ n̍ 永遠是多字元序列）。絕大多數歐文字型都缺少此字形。
韻化輔音 m、n 聲調
ḿ m̀ m̂ m̄ m̍, ń ǹ n̂ n̄ n̍g		 只有 ḿ ń ǹ（及大寫）有預組字元，且 ḿ（U+1E3F）與 ǹ（U+01F9）位於許多歐文字型會跳過的區塊，其餘全需靠組合符號構成。
i 加聲調
í ì î ī ĭ i̍		 i 具有 Unicode Soft_Dotted 屬性：只要上方出現附加符號，原本的點就必須消失。預組的 í 已經去掉點，但 i + U+030D 必須由字型自動替換成無點 ı。
鼻化上標 ⁿ U+207F
SUPERSCRIPT LATIN SMALL LETTER N		 屬於修飾字母（Lm），不是組合附加符號。許多字型缺字；若誤用 NFKC 正規化會把它變成普通 n（見下方）。
連字號 - 與 -- - 連接音節，-- 標示輕聲（如 tńg--khì）。字型與編輯器絕不可將 -- 合併成破折號（見下方）。
漢羅（Han-Lo）與注音 Ruby 漢字字型的歐文區必須具備上述所有支援；漢字上方的 POJ 注音則需透過 IVS（cmap format 14）或網頁 HTML <ruby>（見下方）。
測試時務必牢記的標調位置規則

韻化 ng 的調號標在 n 上面：n̍g、n̂g，絕不是 ng̍。

Unicode 未來會新增單一預組字元 o͘ 或 a̍ 嗎？

不會。所有帶有 U+0358 或 U+030D 的字母都沒有預組字碼，未來也絕不會新增。UTC/WG2 政策明確禁止為「已可用基礎字母＋組合符號表示的字母」新增預組字碼；2005 年 Unicode 4.1 納入 POJ 時便是選擇新增 U+0358。此外，正規化穩定性政策（2001）保證既有字元序列的 NFC 結果永不改變，因此任何新字碼都不可能成為 o + U+0358 的 NFC 形式。

多種輸入編碼與標準組合類別（ccc）

同一個肉眼所見的 ó͘，送到字型時至少有三種不同字元序列，合格的 POJ 字型必須將它們渲染成完全一樣的外觀：

ó͘ 的三種常見編碼形式

編碼形式實際字碼序列常見來源
1. NFC（標準預組形式）U+00F3 ó + U+0358多數網頁文字、主流輸入法、採 NFC 正規化的資料庫
2. NFD（標準分解形式）U+006F o + U+0301 + U+0358macOS 檔名、部分輸入法、從 PDF 複製出來的文字
3. 非正規順序U+006F o + U+0358 + U+0301先輸入 o͘ 整體、再按聲調鍵的序列式／死鍵輸入法
4. 混合形式同一份文件混雜上述 1–3 種經由多個軟體或跨平台編輯過的文件
óU+00F3+  ͘U+0358 ≡ oU+006F+  ́U+0301+  ͘U+0358 ≡ oU+006F+  ͘U+0358+  ́U+0301

標準組合類別（Canonical Combining Class，ccc）

組合附加符號標準組合類別（ccc）
U+0300 0301 0302 0304 0306 030D230（上方 Above）
U+0358 右上圓點232（右上方 Above Right）

Unicode 正規化會依 ccc 由小到大排列相鄰的組合附加符號，因此 o + U+0358 + U+0301 會重排成 o + U+0301 + U+0358，NFC 再將其合成 ó + U+0358。關鍵影響如下：

  • 正規化之後，聲調符號永遠排在右上圓點之前。
  • 第 2、3、5、7、9 調的 NFC 形式都是「預組帶調母音＋U+0358」。字型必須能將 U+0358 掛在 ó ò ô ō ŏ Ó Ò Ô Ō Ŏ 上，而不只是純 o O。
  • 第八調沒有預組母音，因此 o̍͘ 的 NFC 形式仍保持三個字碼：o + U+030D + U+0358。
  • HarfBuzz 會在執行 GSUB 之前先依 ccc 重排並透過 cmap 重新組合。本研究 24 款字型全數驗證：o 0358 0301、o 0301 0358 與 ó 0358 在 HarfBuzz 中產生的字形結果完全相同。因此僅針對非正規順序寫的連字規則在 HarfBuzz 永遠不會觸發——但為了相容不預先正規化的其他整形引擎，仍須一併保留。
  • 若文件混雜多種形式，搜尋 hō͘ 時可能會漏掉其他編碼的項目；將文本統一轉為 NFC 即可解決。

文字整形引擎如何處理 POJ

HarfBuzz（Chrome、Firefox、Android、LibreOffice、Linux）

經本研究實測並對照原始碼 hb-ot-shape-normalize.cc／hb-ot-shape-fallback.cc 確認：

  1. 正規化：先分解、依 ccc 排序，再查字型的 cmap 重新組合（拉丁文使用 COMPOSED_DIACRITICS 模式）。若 cmap 缺少某個預組字母，HarfBuzz 會將其分解為基礎字母＋附加符號。
  2. GSUB ccmp：永遠強制啟用，使用者與 CSS 皆無法關閉；用於無點 i、大寫調號與 POJ 預繪連字。
  3. 其他 GSUB 功能：locl、liga、case 等。
  4. GPOS mark / mkmk：依錨點精準定位附加符號。
  5. 備援定位為「全有或全無」：HarfBuzz 只有在字型完全沒有 GPOS mark 功能時，才會依 ccc 與外框盒估算位置。只要字型含有 mark，卻漏掉某一對字母與符號的錨點，該符號就會直接停在原始偏移 (0, 0)：
    • 已驗證 — Arial：有 mark 但無 U+0358 錨點 → 圓點停在 (0, 0)，掉出字寬之外。
    • 已驗證 — Source Sans 3：ŏ + U+0358 與 Ŏ + U+0358 漏設錨點 → 偏移 (0, 0)。
    • 已驗證 — Geneva、Helvetica、Menlo 與 taigivs 歐文區：完全無 mark → 啟動備援定位，把 U+0358 抬高到 Ó/Ō 含調號的整個筆畫上方，造成大寫圓點高懸。

CoreText（macOS / iOS / Safari）與 DirectWrite（Windows / Word）

驗證狀態說明

macOS CoreText 已進行初步實測（見跨平台差異）；Windows DirectWrite 尚未直接實測，標註（尚未實測）者依據平台規格文件整理。

  • 兩者都不會像 HarfBuzz 那樣用 ccc／外框盒執行備援定位；無錨點符號會畫在字形原始座標上（DirectWrite 尚未實測；CoreText 已觀察到此現象）。
  • DirectWrite 據報不會像 HarfBuzz 一樣在 GSUB 前重排附加符號或透過 cmap 重組 NFD，因此 o + U+0301 可能維持兩個字形，非正規順序也會直接進入 GSUB（審查意見，尚未實測）。
  • 若 cmap 缺少某個預組字母（如 ḿ、ǹ、ŏ），兩者傾向觸發系統補字（font fallback）而非自動分解，導致單一字母變成別款字型（審查意見，尚未實測）。
  • Apple 系統字型（Geneva、Helvetica、Menlo）在 CoreText 下可能改走 AAT 表（morx/kerx），因此 HarfBuzz 的結果無法直接預測 Pages 或 Safari 的顯示效果。

正因如此，一套可靠的 POJ 字型必須在 cmap 完整收錄預組字表中的所有字元，並在 GSUB ccmp 同時涵蓋 NFC、NFD 與反向順序。

Soft_Dotted 的 i 與 j（無點 ı 替換）

當上方附加符號落在 i 上時，原本的點必須消失，就像 í 一樣。預組字元 í ì î ī ĭ 本身已去點，但 i + U+030D（i̍）永遠是組合序列，必須由字型在 ccmp 執行 i → dotlessi（U+0131）與 j → uni0237（U+0237）。

正確chi̍t（一）於 Lesson One：U+030D 之前自動替換為無點 ı
錯誤chi̍t 於字咍 Taigi Huninn POJ：第八調豎線下方仍殘留原本的點

鼻化上標 ⁿ（U+207F）與大寫 ᴺ（U+1D3A）

  • U+207F 是修飾字母（General Category Lm），不是組合附加符號；它本身擁有字寬，不需要錨點。
  • NFKC/NFKD 毀損風險：其相容分解定義為 <super> n，因此 NFKC/NFKD 會默默把 hiⁿ 變成 hin（thiⁿ 變成 thin）。許多搜尋引擎、資料庫與全半形正規化工具預設使用 NFKC，會直接破壞鼻化意義。處理台語文本務必使用 NFC，絕不可用 NFKC。
  • 無大寫對應：Unicode 未定義 U+207F 的大寫轉換，"sⁿ".upper() 結果為 Sⁿ。全大寫標題有時會改用 U+1D3A ᴺ MODIFIER LETTER CAPITAL N（SIᴺ）或 NN；POJ 字型建議一併收錄 U+1D3A。
  • .case 設計規範：ⁿ 的 .case 替代字形可以微調高度以對齊大寫高度，但絕不可把 ⁿ 換成大寫 ᴺ，以免改變字元語意。
  • 非字型問題的誤用：HTML <sup>n</sup>、下標 ₙ（U+2099）與陰性序數 ª 皆屬錯誤編碼。

真實文本中常見的舊式與替代編碼

在 2005 年 U+0358 成為標準之前（以及早期軟體環境），寫作者常以形似字或私用字碼替代：

編碼方式範例處理與轉換建議
標準組合符號 U+0358（Unicode 4.1，2005）o͘唯一標準。字型應提供錨點及／或 ccmp 連字。
中圓點／間距點（U+00B7、U+02D9、U+2022、U+30FB）o·屬於標點，會把單字拆斷並破壞搜尋；應於輸入或前處理時轉為 U+0358。
越南語帶角 o（U+01A1 ơ, ớ, ờ…）ơ完全不同的字母，無法與 o͘ 互通搜尋；應轉為 o + U+0358。
上圓點 U+0307 代 o͘ 或第八調；U+02C8 ˈ 或撇號代第八調ȯ, aˈ語意錯誤；應轉為標準 POJ 組合符號。
ASCII／打字機拼法oo, ou, o', nn, N純 ASCII 權宜寫法；建議轉成標準 POJ 符號以利閱讀與搜尋。
私用區（PUA）與舊 8-bit 編碼U+E400–E435（aiongg／NunitoPOJ）；早期 Windows-1252／MacRoman 0x80–0xFF僅在特定單一字型中有效，換字型即成豆腐字或亂碼。新文本切勿使用；舊字型可視需要保留以讀取歷史文件。
數字調號（POJ 數字式）peh8-oe7-ji7輸入速記格式，交由輸入法或轉換程式轉為 Unicode 調號。

異體字選擇器序列（IVS）漢羅注音字型

ButTaiwan 開發的 字咍 taigivs 系列字型（TaigiHuninn、TaigiIansui、TaigiKaiStd、TaigiGenRyuMin 等；字型採 OFL 1.1），透過 OpenType cmap format 14 表將台語注音直接畫進漢字字形中：

  • 每個漢字後方接上異體字選擇器（U+E0100…），即對應到帶有特定台語讀音的字形——每款字型包含 8,021 筆 IVS 對應。
  • 提供 POJ（白話字）、HI（方音符號）、KN（台語假名），以及雙注音組合 POJHI、POJKN。
  • 僅使用 IVS、不含 GSUB 規則：只要切換字型檔，同一份純文字就能切換不同注音系統。
  • 這是在不使用 HTML <ruby> 的情況下，唯一能於純文字中呈現漢字上方 POJ 注音的方法，與歐文區的 POJ 支援屬於兩條不同路線。
  • 注意事項：taigivs 字型的歐文區沒有 GPOS mark 表也沒有無點 i 替換（i̍ 會留點），因此長篇純 POJ 文章會仰賴 HarfBuzz 備援。此外，網頁子集工具與 PDF 轉檔工具經常會把 cmap format 14 或異體字選擇器刪掉。

連字號與輕聲雙連字號（--）

  • 單連字號 -（U+002D）連接音節；雙連字號 -- 標示輕聲：chhù--nih、khòaⁿ--tio̍h、tńg--khì（轉去）。
  • 字型規則：絕不可透過 liga 或 calt 將 -- 連字成連接號／破折號，且兩條連字號之間應保留適當間距不可黏在一起。
  • 編輯器規則：文書軟體自動將 -- 轉成 – 的「智慧破折號」功能會破壞 POJ，務必關閉。
  • 斷行問題：避免在雙連字號中間換行（chhù- / -nih）屬於排版引擎層級；實務上偶爾會改用 U+2011 不換行連字號，但許多字型未收錄該字碼。
