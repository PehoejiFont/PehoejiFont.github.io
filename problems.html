Troubleshooting & Platform Differences

Diagnose every common Taigi POJ rendering, search, web-delivery, and PDF extraction issue — and understand how HarfBuzz, macOS CoreText, and Windows DirectWrite behave differently.

Symptom-by-symptom diagnosis

1. Empty boxes (□ / tofu) appear instead of letters or marks

Cause: The font’s cmap lacks that codepoint entirely. For example, EB Garamond has no U+0358, and 1,242 of 1,393 shortlisted Google Fonts families lack all three POJ codepoints (U+0358, U+030D, U+207F).

Fix: Switch to a verified font from the recommended list.

2. The dot of o͘ lands far to the right, or floats high above capitals

Cause: The font maps U+0358 without a topright anchor (Technique D). If the font has a mark table for other accents (like Arial or Source Sans 3 on ŏ͘), HarfBuzz disables fallback and leaves the dot at offset (0, 0). If it has no mark table at all (like Helvetica/Geneva/Menlo), HarfBuzz fallback lifts the dot above the full ink box of Ó͘ Ō͘.

Fix: Switch to an A+B or A font. Never add manual spaces or hand-kerning, which breaks on every other viewer’s screen.

3. One letter in a word looks like a different typeface

Cause: The font lacks that specific precomposed codepoint (commonly ḿ U+1E3F, ǹ U+01F9, ŏ, U+0358, or U+030D), so the OS or browser silently borrows it from a system fallback font (for instance, on macOS, EB Garamond borrows U+0358 from Helvetica).

Fix: Choose a font that maps the full POJ precomposed set (verify in the Test Bench).

4. A dot stays underneath the tone line on i̍

Cause: The font fails to implement the Soft_Dotted substitution (i → dotlessi in ccmp before above-marks; details). Observed in 字咍 Taigi IVS fonts, EB Garamond, Helvetica, Geneva, and Menlo.

Fix: Switch fonts. Never type dotless ı (U+0131) manually in running text — it breaks spelling and search matching.

5. Text breaks when CSS letter-spacing is added or when opened in Microsoft Word

Cause: The font implements POJ glyph building inside optional liga or clig rather than mandatory ccmp. CSS Text 3 disables optional ligatures under non-zero letter-spacing, and Microsoft Word leaves ligatures off by default.

Fix: Use a font that puts POJ composition in ccmp (all fonts in our recommended list do). As a temporary workaround in Word, enable ligatures under Font → Advanced.

6. thiⁿ silently turned into thin (or hiⁿ into hin)

Cause: A database, search indexer, or “normalise text” script applied NFKC/NFKD, which decomposes U+207F via <super> n into plain ASCII n (details).

Fix: Always configure text pipelines, databases, and search indexers to use NFC — never NFKC or NFKD — for Taigi data.

7. Ctrl+F / database search misses a word visible on screen

Cause: Either the text mixes NFC (ó + 0358), NFD (o + 0301 + 0358), and reverse order (o + 0358 + 0301), or it contains legacy look-alikes such as middle dot o· (U+00B7) or Vietnamese horn ơ (U+01A1).

Fix: Replace legacy look-alikes with standard U+0358/U+030D/U+207F and normalise the corpus to NFC.

8. Neutral-tone tńg--khì turned into an en-dash tńg–khì

Cause: Word-processor “smart dashes” auto-corrected two hyphens into an en-dash, or a font has a liga/calt ligature turning -- into a dash.

Fix: Disable “replace hyphens with dash” in editor auto-correct settings, and verify -- stays two hyphens in the font.

9. POJ looks right locally, but breaks on my website

Cause: Loading the font via Google Fonts CSS API serves unicode-range subsets that drop U+0358, U+030D, and U+207F for families like TASA Explorer and Source Sans 3 (verified audit). Aggressive local subsetters (pyftsubset) can also strip ccmp/mark or cmap format 14.

Fix: Self-host the full font file, or subset explicitly keeping all POJ codepoints and --layout-features='*'.

10. Old documents show strange symbols or boxes after changing fonts

Cause: Legacy POJ documents used Private Use Area slots (e.g. U+E400–E435 in older aiongg fonts) or pre-Unicode 8-bit Windows-1252 / MacRoman remappings that only exist in one specific font.

Fix: Run a one-time conversion from the legacy PUA/8-bit encoding to standard Unicode NFC POJ.

11. Copying POJ text out of a PDF produces garbage, extra spaces, or dotless ı

Cause: Three distinct PDF issues: (a) non-standard glyph names (e.g. oopoj_acutecomb instead of AGL-compliant o_uni0301_uni0358) break automatic ToUnicode CMap generation; (b) SIL’s spacing dot (Way C) may cause PDF viewers to infer a word space; (c) dotlessi + uni030D can extract as ı̍ unless the PDF producer emits /ActualText.

Fix: Use fonts with AGL-compliant production names, and ensure PDF generators emit proper /ActualText spans where supported.

Platform & shaping engine differences

Web browsers (Chrome, Firefox), Android, LibreOffice, and Linux all use HarfBuzz. Native Apple apps (Safari, Pages, Keynote) use CoreText, and native Windows apps (Microsoft Word, Edge/Windows UI) use DirectWrite.

EngineUsed byTest status in this projectKey POJ behaviours
HarfBuzz Chrome, Firefox, Android, LibreOffice, Linux Fully tested (24 fonts) Normalises (ccc reorder + cmap recompose) before GSUB. Decomposes missing precomposed letters. Geometric fallback is all-or-nothing (disabled whenever any mark feature exists).
CoreText macOS / iOS native apps, Safari, Pages Preliminary tests Lesson One, jf open 粉圓, 芫荽 Iansui, I.Ming, GenYo Min, and WD-XL Lubrifont produced identical glyph runs to HarfBuzz across all test clusters. Fonts lacking mark (Helvetica, Menlo, 字咍 Taigi fonts) differ markedly because CoreText does not use HarfBuzz fallback and Apple system fonts may use AAT (morx/kerx).
DirectWrite Windows native apps, Microsoft Word Not yet tested (Reviewer claims, unverified): Does not pre-reorder or recompose NFD like HarfBuzz, so non-canonical sequences reach GSUB; missing precomposed letters trigger system font fallback rather than decomposition; Word leaves liga off by default.
How to stay platform-independent

Choose fonts built with Techniques A + B (ccmp precomposed glyphs covering NFC, NFD, and reverse order, backed by complete GPOS mark/mkmk anchors and full precomposed cmap coverage). They behave identically across HarfBuzz, CoreText, and DirectWrite.
